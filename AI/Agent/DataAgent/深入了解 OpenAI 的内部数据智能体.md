> [深入了解 OpenAI 的内部数据智能体](https://openai.com/zh-Hans-CN/index/inside-our-in-house-data-agent/)

数据为系统如何学习、产品如何演进以及企业如何做出选择提供动力。但要快速、准确地获取答案，并结合相关上下文，往往比想象中更为困难。随着 OpenAI 业务范围的扩展，为了简化这项工作，我们建立了专属定制内部 AI 数据智能体，通过 OpenAI 的平台进行探索和推理。

我们的智能体是一款定制内部专用工具（非外部产品），围绕 OpenAI 的数据、权限和工作流而构建。我们将展示 OpenAI 如何构建和使用这一工具，以帮助大家了解 AI 如何以切实可行的方式，支持团队完成日常工作。我们用于构建和运行这一智能体的 OpenAI 工具（Codex、我们的 GPT‑5 旗舰模型、Evals API⁠（在新窗口中打开） 和 Embeddings API⁠（在新窗口中打开））与我们面向全球各地开发人员提供的工具相同。

我们的数据智能体可支持员工在几分钟（而非几天）内从问题中提取洞察数据。这降低了所有职能部门（而不仅仅是我们的数据团队）提取数据和进行细致分析的门槛。如今，OpenAI 的工程、数据科学、市场进入、财务和研究团队都依赖智能体来解答高价值数据问题。例如，它可以通过直观的自然语言格式，回答如何评估发布流程和理解业务运行状况等问题。该智能体结合了 Codex 驱动的表格级知识，以及产品和组织的背景信息。其持续学习记忆系统意味着它能够不断优化。

在这篇文章中，我们将深入分析为什么我们需要定制 AI 数据智能体，代码增强型数据上下文和自学习功能为何如此重要，以及我们在此过程中汲取的经验教训。

## 1. 为什么我们需要定制工具

OpenAI 的数据平台为工程、产品和研究部门的 3,500 多名内部用户提供服务，涵盖 70,000 个数据集中超过 600 PB 的数据。在此规模下，寻找合适的表可能是分析过程中最耗时的环节之一。

正如一位内部用户所解释的：
```
“我们有很多非常相似的表，我曾耗费大量时间去厘清它们的不同之处，以及具体应选择哪一个表。有的表包括已注销用户，有的则不包括这些用户。有的表存在重叠字段，很难分辨具体内容。”
```
即使选择了正确的表，生成正确的结果也并非易事。分析师必须对表数据和表关系进行推理，以确保正确应用转换和筛选功能。常见的失败模式 — 多对多连接、筛选条件下推错误和未处理的空值，都可能会在不知不觉中输出无效结果。鉴于 OpenAI 庞大的组织架构，分析师不应将时间浪费在调试 SQL 语义或查询性能上：他们的重点应放在定义指标、验证假设和制定数据驱动的决策。

![](https://images.ctfassets.net/kftzwdyauwt9/5AgsmVnLabpc9aeVprgl9n/53c658c2ca42b90ed715045dc3365566/Desktop-Dark.png?w=3840&q=80&fm=webp)

这条 SQL 语句长达 180 多行。要确认我们是否连接正确的表并查询相关列，并非易事。

## 2. 工作原理

让我们逐步了解 OpenAI 的智能体及其如何整理上下文并不断自我完善。

我们的智能体由 GPT‑5.2 驱动，旨在通过 OpenAI 的数据平台进行推理。无论员工在何处办公，都可以使用这一工具：它能够充当 Slack 智能体、通过 Web 界面、嵌入集成开发环境 (IDE)、经由 MCP 连接的 Codex CLI⁠（在新窗口中打开） 以及直接通过 MCP 连接器在 OpenAI 的内部 ChatGPT 应用中调用⁠（在新窗口中打开）。

![](https://images.ctfassets.net/kftzwdyauwt9/45tj3Vpk3ptc4kTOhUnfQk/a443d85b8a3ab8633206498e58282c54/oai_in-house_data_agent_How_it_works_desktop-dark.svg?w=3840&q=80)

用户可以提出复杂的开放式问题，这通常需要多轮人工探索。以使用测试数据集的提示为例：“For NYC taxi trips, which pickup-to-dropoff ZIP pairs are the most unreliable, with the largest gap between typical and worst-case travel times, and when does that variability occur?”

从理解问题到探索数据、运行查询和汇总结果，智能体可负责执行端到端分析。

![](https://images.ctfassets.net/kftzwdyauwt9/4g30UoN8GBkdeUciQ6Wkra/cf30463db8033d5276d009bbe28ff06e/Desktop-Dark.png?w=3840&q=80&fm=webp)

> 智能体对问题的答复。

智能体的一项核心优势在于其解决问题的推理能力。智能体并非遵循固定的脚本，而是会自行评估流程进展。如果某个中间结果出现异常（例如，由于错误的连接或筛选操作导致行数为零），智能体就会调查出现问题的具体环节，调整其方法，并再次尝试。在此过程中，它会保留完整的上下文，并在各步骤之间传递学习成果。这一闭环、自学习过程可将迭代任务从用户转移到智能体自身，从而更快输出结果，并持续提供质量远高于手动工作流的分析数据。

![](https://images.ctfassets.net/kftzwdyauwt9/2GRmgUjPOMpOAmkKfwQjVf/c0435b317be41c17ee759b44c93bca85/oai_in-house_data_agent_NYC_pickup-dropoff_pairs_dark.png?w=3840&q=80&fm=webp)

> 智能体可凭借推理能力，识别最不可靠的纽约市出租车上车点-下车点配对数据。

该智能体现已涵盖完整的分析工作流：发现数据、运行 SQL、发布笔记及报告。它能够理解企业内部知识，通过网络搜索获取外部信息，并不断积累记忆以实现持续优化。

## 3. 上下文决定一切

高质量的答案取决于丰富、准确的上下文。在缺乏上下文的情况下，即使是强大的模型也可能会输出错误结果，例如严重误估用户量或曲解内部术语。

![](https://images.ctfassets.net/kftzwdyauwt9/1AlnC3YBUfUem8XzhNiQii/aedb368e0a9fb807712494da5fb3617c/oai_in-house_data_agent_faster_queries_fast_desktop-dark.png?w=3840&q=80&fm=webp)

> 第一个：没有记忆能力的智能体，无法有效进行查询；第二个：智能体的记忆可通过定位正确的表，加快查询速度。

为了避免这些失败模式，我们围绕多层上下文构建智能体，并以 OpenAI 的数据和机构知识为根基。

![](https://images.ctfassets.net/kftzwdyauwt9/1e0UXiK99kqjFdEOipBUQM/12fd86e7463f04cf2d0f5bb1fdeced24/oai_in-house_data_agent_Layers_of_context_desktop-dark.svg?w=3840&q=80)

> 数据智能体的上下文层次，从下到上分别是：表使用情况、人工注释、Codex 增强、机构知识、记忆、运行时上下文

### 3.1 表使用情况

- 元数据基础：智能体依赖 Schema 元数据（列名和数据类型）来指导 SQL 编写，并使用表血缘（例如，上游和下游表关系）来理解不同表之间的上下文。
- 查询推理：采集历史查询有助于智能体理解如何编写查询，以及哪些表通常相互关联。

### 3.2 人工注释

- 精选描述：由领域专家精心整理的表和列相关描述，用于记录意图、语义、业务含义，以及无法从 Schema 或过往查询中轻易推断的已知注意事项。

> 仅靠元数据是不够的。要真正区分不同表，你需要了解其创建方式及来源。

### 3.3 Codex 增强

- 通过推导表的代码级定义，智能体能够更深入地理解数据的实际内容。
  - 关于表中存储的内容以及如何根据分析事件中得出的细微差别提供额外的信息。例如，它可以提供关于值的唯一性、表数据更新频率、数据范围（例如，如果表排除某些字段，即标识其具备相应的粒度级别）等上下文。
- 通过展示如何在 Spark、Python 和其他数据系统中使用 SQL 以外的表，提供更丰富的使用情况上下文。
- 这意味着，智能体可以区分内容相似但存在关键差异的表。例如，它可以判断某个表是否仅包含第一方 ChatGPT 流量。该上下文还会自动刷新，因此无需手动维护即可保持更新。

![](https://images.ctfassets.net/kftzwdyauwt9/4vo6KqTVvFDJrzXwe947Aa/f9113ed440d61507a0468a788957b066/oai_in-house_data_agent_codex-enriched_knowledge_pipeline_desktop-dark.svg?w=3840&q=80)

### 3.4 机构知识

- 智能体可以访问 Slack、Google Docs 和 Notion，这些平台记录了关键的企业背景信息，例如产品发布、可靠性事件、内部代号和工具，以及关键指标的规范定义和计算逻辑。
- 这些文档会被采集、嵌入，并与元数据和权限一起存储。检索服务可在运行时处理访问控制和缓存，支持智能体高效且安全地获取这些信息。

![](https://images.ctfassets.net/kftzwdyauwt9/6z6uxXjEI454qqphYu43UK/43042c9faf92fe45e21e6ceb82ca60bc/Desktop-Dark.png?w=3840&q=80&fm=webp)

### 3.5 记忆

- 当智能体收到更正信息或发现某些数据问题存在细微差别时，它能够保存这些学习结果以供后续使用，从而在与用户交互的过程中持续改进。
  - 因此，未来的答案将以更准确的基线为切入点，而非反复处理相同的问题。
  - 记忆的目标是保留并复用那些不易察觉的更正信息、过滤条件和约束限制，这些内容对于维持数据的正确性至关重要，但仅凭其他层级难以有效推断。
  - 例如，在某个案例中，智能体不知道如何筛选特定的分析实验（它需要依赖与实验门中定义的特定字符串进行匹配）。在此过程中，记忆至关重要，因为这一能力可确保智能体正确筛选相关信息，而非盲目尝试进行字符串匹配。
- 当你向智能体提出更正意见，或者当其从对话中查找学习内容时，它会提示你保存记忆，以备后续使用。
  - 用户也可以手动创建和编辑记忆。
  - 记忆的范围涵盖全局和个人层面，而智能体所配备的工具将简化编辑流程。

![](https://images.ctfassets.net/kftzwdyauwt9/4wl8sFZO1MFveE2FZw7qvC/7e30e71979c8a43b800e5ed5716d0b2c/Desktop-Dark.png?w=3840&q=80&fm=webp)

### 3.6 运行时上下文

- 如果表缺乏先前的上下文或现有信息过时，智能体可以向数据仓库发起实时查询，以直接检查和查询该表。这使其能够验证 Schema、实时理解数据，并做出相应的回复。
- 该智能体还能根据需要与其他数据平台系统（元数据服务、Airflow、Spark）进行对话，以获取数据仓库之外更广泛的数据上下文。

我们运行一条每日离线 Pipeline，将表使用情况、人工标注以及Codex派生的增强信息聚合到一个统一的规范化表示中。然后，该增强上下文通过 OpenAI 嵌入 API 转换为向量并存储，以供检索。在查询时，智能体仅通过检索增强生成（RAG）拉取最相关的嵌入上下文，而无需扫描原始元数据或日志。这使得表理解变得快速且可扩展，即使面对数万张表也能保持运行时的低延迟。运行时查询会根据需要实时发送到我们的数据仓库执行。

![](https://images.ctfassets.net/kftzwdyauwt9/u90x8VCsIVfWMACdsky6Y/cd3691359ca1e3aeb04b5cdfe1cd21d0/oai_in-house_data_agent_context_retrieval_desktop-dark.svg?w=3840&q=80)

综上所述，这些层协同作用，使智能体的推理以 OpenAI 的数据、代码和内部知识为根基，大幅降低出错率，同时提升答案的准确度。

## 4. 像队友一样思考和工作

一次性回答在问题很明确时很有效，但大多数问题都不是这样。更多时候，要得到正确结果，往往需要来回反复地完善和适当的方向修正。该智能体的设计理念是像一个可以与之共同推理的队友。它采用对话式、始终在线的方式，既能处理快速问答，也能应对迭代式探索。

它会在多轮对话中保留完整的上下文，因此用户可以提出后续问题、调整意图或改变方向，而无需重复所有前提信息。如果智能体开始偏离正确路径，用户可以在分析过程中中断并重新引导它，就像与一位善于倾听而非固执己见的人类协作者一起工作一样。

当指令不清晰或不完整时，智能体会主动提出澄清性问题。如果用户未作回复，它会应用合理的默认设定来推进任务。例如，如果用户询问业务增长但未指定日期范围，它可能会默认采用最近 7 天或 30 天的数据。这些预设（先验）使其能够保持响应迅速且不阻塞流程，同时仍能逐步趋近正确结果。

最终效果是：该智能体既能在您明确知道自己想要什么时（例如“告诉我关于这张表的信息”）表现出色，也能在您进行探索性提问时（例如“我看到这里有一个下降趋势，能否按客户类型和时间维度拆解分析？”）同样强劲有力。

上线后，我们观察到用户经常对常规重复性工作运行相同的分析。为了加速这类操作，智能体的工作流功能将重复性分析封装为可复用的指令集，例如用于每周业务报告和表验证的工作流。通过一次性将上下文和最佳实践编码其中，工作流能够简化重复分析流程，并确保不同用户获得一致的结果。

![](https://images.ctfassets.net/kftzwdyauwt9/6jAwY8VgVCqHRbpEgdpA0Y/b5c8b3f6b949c048d00723132832a9d1/Desktop-Dark.png?w=3840&q=80&fm=webp)

## 5. 快速前进而不破坏信任

构建一个始终在线、持续进化的智能体，意味着质量既可能提升，也同样可能下滑。如果没有紧密的反馈闭环，回归问题将不可避免且难以察觉。要在不破坏信任的前提下扩展能力，唯一途径是进行系统化评估。

在本节中，我们将讨论如何利用 OpenAI 的 Evals API 来衡量并保障智能体的回答质量。Evals 基于精心筛选的问答对数据集构建。每个问题都针对我们高度重视的某项关键指标或分析模式，并配有人工编写的“黄金”SQL 查询，该查询可产生预期结果。对于每次评估，我们将自然语言问题发送到查询生成端点，执行生成的 SQL，然后将输出结果与预期 SQL 的结果进行比对。

![](https://images.ctfassets.net/kftzwdyauwt9/15eSmOlfqTBZcxErAdzAbU/1dd9b1e550d1f9b3ed0e4c23dc662db2/oai_in-house_data_agent_eval_pipeline_desktop-dark.svg?w=3840&q=80)

评估并不依赖简单的字符串匹配。生成的 SQL 可能在语法上有所不同，但结果仍然正确；结果集中也可能包含多余的列，而这些列对答案没有实质性影响。为应对这种情况，我们会同时比较 SQL 语句和结果数据，并将这些信号输入 OpenAI 的 Evals 评分器（grader）。评分器会生成最终得分并附上解释，同时兼顾正确性和可接受的差异变化。

这些评估就像单元测试一样，在开发过程中持续运行，用于识别回归问题；同时在生产环境中充当预警信号（canary），使我们能够尽早发现问题，并在智能体能力不断扩展的过程中自信地进行迭代。

## 6. Agent 安全性

我们的智能体直接接入 OpenAI 现有的安全与访问控制模型。它纯粹作为一个接口层运行，继承并执行与 OpenAI 数据治理相同的权限和防护机制。

智能体的所有访问均为严格的透传方式（pass-through），即用户只能查询其已有权限访问的表。当权限不足时，系统会予以标记，或回退到用户被授权使用的替代数据集。

最后，该智能体以透明为设计原则。与任何系统一样，它也可能犯错。它会通过在每个答案旁边总结假设条件和执行步骤来暴露其推理过程。当查询被执行时，它会直接链接到底层结果，使用户能够检查原始数据并验证分析的每一个步骤。

## 7. 经验教训

从零构建我们的智能体，让我们在实际中学到了关于智能体行为模式、容易出错的环节以及真正让它们在规模上变得可靠的关键要素。

### 7.1 经验#1：少即是多

早期，我们向智能体暴露了完整的工具集，很快就遇到了功能重叠带来的问题。虽然这种冗余对某些特定定制场景可能有帮助，而且人工手动调用时也更容易察觉，但对智能体来说却会造成困惑。为了减少歧义、提高可靠性，我们对某些工具调用进行了限制和整合。

### 7.2 经验#2：引导目标，而非路径

我们还发现，过于细致的规定性提示会降低结果质量。尽管许多问题在分析框架上具有共性，但具体细节差异很大，僵化的指令往往会把智能体推向错误的路径。通过转向更高层次的引导，并依赖 GPT‑5 的推理能力来选择适当的执行路径，智能体变得更加稳健，效果也更好。

### 7.3 经验#3：意义存在于代码之中

表结构和查询历史描述了一张表的形态和使用情况，但其真正含义存在于生成它的代码中。Pipeline 逻辑包含了假设条件、时效性保障以及业务意图，而这些从未出现在 SQL 或元数据中。通过用 Codex 爬取代码库，我们的智能体能够理解数据集的实际构建方式，并更好地推理每个表实际包含的内容。它能比单纯依赖仓库信号更准确地回答“这里面有什么”以及“我什么时候可以用它”这类问题。

## 8. 愿景不变，工具更新

我们正在持续改进智能体，不断增强其处理模糊问题的能力，通过更强的验证机制提升可靠性与准确性，并将其更深入地集成到工作流中。我们相信，它应该自然而然地融入人们现有的工作方式，而不是作为一个独立的工具来运作。

虽然我们的工具将持续受益于智能体推理、验证和自我纠正等底层能力的进步，但我们团队的使命始终如一：在 OpenAI 的数据生态系统中，无缝提供快速、可信的数据分析。

pen Knowledge Format(OKF) 是一种开放的、对人类和智能体（Agent）都友好的知识表示格式：它承载围绕数据与系统的元数据、上下文和经过整理的洞察。它被设计为可以由人类撰写、由智能体生成、跨组织交换，并被双方消费。

该格式刻意保持极简：一个由带 YAML frontmatter 的 Markdown 文件组成的目录。没有 Schema 注册中心，没有中央权威机构，也没有强制要求的工具链。只要你会 `cat` 一个文件，你就能读取 OKF；只要你会 `git clone` 一个仓库，你就能分发它。

本文档是自包含的：它规定了生产和消费 OKF v0.2 所需的一切。相对于 v0.1 的变更摘要见 §13。

---

## 1. 动机

面向 AI 智能体的知识表示领域正在快速演化，许多互不兼容的约定正在涌现。OKF 主张：知识最好用通用的、成熟的、具备以下特性的格式来表示：

- 人类无需工具即可阅读。
- 智能体无需定制 SDK 即可解析。
- 可在版本控制中做差异对比（diff）。
- 可跨工具、跨组织、跨时间移植。

越来越多的知识语料不再是"一次撰写、反复阅读"，而是由智能体持续编写和维护。当大多数概念都是机器生成时，消费者需要回答一些纯粹的"Markdown + frontmatter"约定没有将其作为一等公民对待的问题：

1. 它是从什么创建的，又是如何被验证的？（来源溯源，provenance）
2. 我应该在多大程度上信任它？（信任度，trust）
3. 它现在还成立吗？（新鲜度，freshness）
4. 它是当前版本吗？（生命周期，lifecycle）
5. 这个数字是按照我们规定的方式产出的吗？（认证，attestation）

OKF v0.2 将来源溯源、信任度、生命周期和认证作为一等公民，同时保持格式的最小主张性。格式是最小主张的：它只标准化使知识语料自描述所需的一小组结构约定——其余一切留给生产者决定。

### 目标

1. 定义一种通用格式，供生产者（人类、智能体、导出流水线）写入。
2. 指导消费者（智能体、UI、搜索索引、确定性代码）应如何读取和遍历它。
3. 促进知识跨系统、跨组织交换。
4. 标准化一小组使智能体维护的语料可被信任的 frontmatter 字段，但不规定任何运行时。

### 非目标

- 定义固定的概念类型分类体系（taxonomy）。
- 规定存储、服务或查询基础设施。
- 取代领域特定的 Schema（Avro、Protobuf、OpenAPI 等）。OKF 引用它们，而不是吞并它们。
- 为执行器（executor）或认证器（attester）所指向的代码规定打包或调用标准。OKF 固定的是接口，而非打包方式。

## 2. 术语

- **知识包（Knowledge Bundle，简称 bundle）**：知识文档的自包含层级集合，是分发单元。
- **概念（Concept）**：bundle 中的单个知识单元，用一个 Markdown 文档表示。它可以描述有形资产（一张表、一个 API）、抽象概念（一个指标、一个业务流程），或介于两者之间的任何东西。
- **概念 ID（Concept ID）**：概念文件在 bundle 内的路径，去掉 `.md` 后缀。
- **Frontmatter**：Markdown 文件顶部以 `---` 分隔的 YAML 元数据块。
- **正文（Body）**：文件中 frontmatter 之后的所有内容。
- **链接（Link）**：从一个概念指向另一个概念的标准 Markdown 链接，用于表达隐式父子层级之外的关系。
- **来源（Source）**：概念所派生的材料（bundle 外部或内部），记录在 frontmatter 的 `sources` 字段中。
- **来源溯源（Provenance）**：概念所派生的来源集合。
- **可信度信号（Credibility signal）**：客观的、按来源记录的事实（`author`、`usage_count`、`last_modified`），用于推断信任度；OKF 记录的是信号，而非结论（见 §5.1）。
- **参与者（Actor）**：标识谁或什么执行了某个动作的字符串，约定为：智能体用 `<producer>/<version>`，人类用 `human:<id>`，自动化流程用 `process:<id>`（见 §7）。
- **信任等级（Trust tier）**：由概念的 `verified` 字段派生的等级：`unverified`（未验证）、`machine-confirmed`（机器确认）、`human-reviewed`（人工复核）（见 §5.3）。
- **认证计算（Attested Computation）**：携带一种被认可的数值计算方式的概念（`type: Attested Computation`），使消费者可以通过运行它来确认数值确实是这样产出的（见 §10）。
- **执行器（Executor）**：运行执行计算的指令或代码，并返回一张回执（receipt）（见 §10.2）。
- **回执（Receipt）**：一次运行所返回的证据，其形状由 `executor.receipt` 定义；它是运行时产物，不存储在 bundle 中（见 §10）。
- **认证器（Attester）**：检查回执并给出结论（verdict）的确定性（无 LLM）代码（见 §10.2）。

## 3. Bundle 结构

bundle 是一个由 Markdown 文件组成的目录树。目录结构与领域无关：生产者可以按对所要沉淀知识最合理的方式组织概念。
```
path/to/bundle/
  index.md                      # 可选。用于渐进式披露的目录清单。
  log.md                        # 可选。按时间排列的更新历史。
  <concept>.md                  # 位于 bundle 根目录的一个概念。
  <subdirectory>/               # 子目录把概念组织成组。
    index.md
    <concept>.md
    <subdirectory>/
      ...
```

bundle 可以按以下方式分发：
- Git 仓库（推荐，因为它提供历史、署名和 diff）。
- 目录的 tarball 或 zip 压缩包。
- 更大仓库中的一个子目录。

### 3.1 保留文件名

以下文件名在层级的任何位置都具有特定含义，**不得** 用于概念文档：

| 文件名 | 用途 |
| --- | --- |
| `index.md` | 目录清单。见 §8。 |
| `log.md` | 更新历史。见 §9。 |

所有其他 `.md` 文件都是概念文档。

标签（tags）通过 `tags` frontmatter 字段（§4.1）保持一等公民地位。OKF 不规定按标签聚合文档的独立文件格式；想要标签浏览视图的消费者可以在消费时通过扫描 frontmatter 自行合成。

## 4. 概念文档

每个概念都是一个 UTF-8 编码的 Markdown 文件，包含两部分：

1. 一个 YAML frontmatter 块：以独占一行的 `---` 开始，以独占一行的 `---` 结束。
2. 一个 Markdown 正文：包含自由格式的内容。

### 4.1 Frontmatter

```yaml
---
type: <类型名称>                  # 必填（REQUIRED）
title: <可选的显示名称>
description: <可选的一行摘要>
resource: <底层资产的可选规范 URI>
tags: [<标签>, <标签>, ...]        # 可选
# ... 信任、生命周期、来源溯源与计算字段族（见 §5、§10）
# ... 其他生产者自定义的键值对
---
```

**必填项：**

- `type`：标识概念种类的短字符串。消费者用它做路由、过滤和展示。示例取值：`BigQuery Table`、`BigQuery Dataset`、`API Endpoint`、`Metric`、`Playbook`、`Reference`、`Attested Computation`。类型取值不做中心化注册。生产者**应当（SHOULD）**选择具描述性、自解释的值；消费者**必须（MUST）**优雅地容忍未知类型，通常做法是将其视为通用概念对待。

`type` 是唯一始终必填的键；一个只带 `type` 的概念完全合规（§11）。

**推荐项：**

- `title`：人类可读的显示名称。若省略，消费者**可以（MAY）**从文件名派生标题。
- `description`：概述该概念的一句话。供 index.md 生成器、搜索摘要和预览使用。
- `resource`：唯一标识该概念所描述的底层资产的 URI。对于描述抽象概念而非物理资源的概念，此字段缺省。
- `tags`：用于横切分类的短字符串 YAML 列表。

可选的来源溯源、信任、生命周期字段族（§5）以及认证计算概念的各计算字段（§10）也可能出现。

**扩展：** 生产者**可以（MAY）**加入任意附加键。消费者在回写（round-tripping）时**应当（SHOULD）**保留未知键，并且**必须不（MUST NOT）**因无法识别的字段而拒绝文档。

### 4.2 正文

正文是标准 Markdown。生产者**应当（SHOULD）**优先使用结构化 Markdown（标题、列表、表格、围栏代码块）而非自由散文，因为结构既利于人类阅读，也利于智能体检索。

没有强制要求的正文小节。以下标题具有约定含义，适用时**应当（SHOULD）**使用：

| 标题 | 用途 |
| --- | --- |
| `# Schema` | 对资产列/字段的结构化描述。 |
| `# Examples` | 具体使用示例，通常以围栏代码块呈现。 |
| `# Computation` | 认证计算所认可的计算过程。见 §10。 |

针对外部来源的逐条论断归因使用 Markdown 脚注，以 `sources` 条目为键，而不是正文中的引用列表（§5.1）。

### 4.3 示例：绑定到资源的概念

```markdown
---
type: BigQuery Table
title: Customer Orders
description: One row per completed customer order across all channels.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, orders, revenue]
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-05-28T14:30:00Z }
---

# Schema

| Column        | Type      | Description                              |
|---------------|-----------|------------------------------------------|
| `order_id`    | STRING    | Globally unique order identifier.        |
| `customer_id` | STRING    | Foreign key into [customers](/tables/customers.md). |
| `total_usd`   | NUMERIC   | Order total in US dollars.               |
| `placed_at`   | TIMESTAMP | When the customer submitted the order.   |

# Joins

Joined with [customers](/tables/customers.md) on `customer_id`.
```

### 4.4 示例：未绑定资源的概念

```markdown
---
type: Playbook
title: "Incident response: data freshness alert"
description: Steps to triage a freshness alert on the orders pipeline.
tags: [oncall, incident]
generated: { by: human:ahormati, at: 2026-04-12T09:00:00Z }
---

# Trigger

A freshness alert fires when `orders` lags more than 30 minutes behind its
expected SLA. See the [orders table](/tables/orders.md).

# Steps

1. Check the [ingestion job dashboard](https://example.com/dash).
2. ...
```

## 5. 来源溯源、信任与生命周期

这些 frontmatter 字段族使得"它从哪来"、"我该多信任它"、"它现在还有效吗"都可以直接从 frontmatter 中得到回答。它们全部可选。它们的缺省本身带有含义：一个未经验证的概念可以与已验证的概念区分开来，但永远不会被拒绝（§11）。

OKF 中所有取值为时间戳的键都是带显式 UTC 偏移的 ISO 8601 日期时间，例如 `2026-06-30T14:00:00Z`。

### 5.1 来源溯源：sources

`sources` 记录概念所派生的材料，可以是 bundle 外部或内部的。

```yaml
sources:
  - id: ga4-schema
    resource: https://developers.google.com/analytics/bigquery/export-schema
    title: GA4 BigQuery Export schema
    author: team:ga4-docs
    usage_count: 5000
    last_modified: 2026-05-30T00:00:00Z
    usage_window: { from: 2026-06-01T00:00:00Z, to: 2026-06-30T00:00:00Z }
```

每个 `sources` 条目：

- `resource`：条目内**必填**。可以是一个消费者可追踪的具体产物（绝对 URL、bundle 相对路径，或指向 `references/` 子目录的路径，§6），也可以是消费者无法直接追踪的群体或范围描述符（例如 BigQuery 项目 X 中的所有查询）。
- `id`：可选。用于对单条论断做归因的稳定键（见下文）。当正文引用该来源时**应当（SHOULD）**提供。
- `title`：可选。来源的人类可读标签。
- 可选的可信度信号 `author`、`usage_count` 和 `last_modified`，如下所述。

**来源可信度信号。** OKF 记录客观的、按来源维度的信号，让消费者通过评判概念所提取自的来源来评判对该概念的信任程度。它不存储可信度分数：分数是主观的、跨消费者不可移植的，而且会过时。可信度是从信号推断出来的，方式与信任等级相同（§5.3），是被推断而非被存储的。每个信号都是可选的，且挂在 `sources` 条目上：

- `author`：谁或什么产出了该来源，遵循参与者约定（§7）。这是一个权威性信号。
- `usage_count`：`resource` 在 `usage_window` 期间被使用的次数（仪表盘浏览量、查询执行次数、页面阅读次数）。这是一个采用度和活跃度信号。对于单一产物，它是该产物自身的使用次数；对于范围描述符，它是该范围内触及该概念的使用次数。
- `last_modified`：来源本身最后一次变更的时间。这是一个新近度信号，与 `generated.at`（§5.2）不同——后者记录的是概念被写下的时间。
- `usage_window`：作为 `sources` 的同级字段只写一次，它为每个 `usage_count` 框定一个 `{ from, to }` 的日期时间范围。单个条目**可以（MAY）**携带自己的 `usage_window` 以覆盖共享值。

`usage_count` 是一个粗粒度信号。它可以在"活跃 vs 死亡"层面和数量级层面比较，也可以与该来源自身随时间的历史比较，但不能作为跨类型的精确排名：一次定时查询的执行与一次人类有意的仪表盘浏览并不等权。消费者**应当（SHOULD）**将其读作活跃度与趋势，而非分数。

血缘（lineage）通过链接表达，而非专用字段。当一个 `resource` 指向另一个 OKF 概念时，派生边已存在于 bundle 图中（§6），因此消费者**可以（MAY）**递归进入该来源自身的 sources，让可信度沿链传播。外部叶子来源只携带其固有信号。更深层的血缘（显式的外部 `derived_from` 或数据血缘）不在 v0.2 范围内。

**逐条论断归因。** 要对某条具体论断做归因，使用标签为 `sources[].id` 的 Markdown 脚注：

```markdown
The `events_` table is sharded daily as `events_YYYYMMDD`.[^ga4-schema]

[^ga4-schema]: GA4 BigQuery Export schema
```

脚注标签是连接 `sources` 的键；消费者通过匹配的条目解析归因，而不是解析脚注的文字内容。标签按 id 索引而非按位置索引（`sources[0]`），因为智能体会不断改写这些文档：位置索引在列表重排的瞬间就会悄无声息地归因错误，而稳定的 id 能在重排后依然有效。

### 5.2 信任：generated 与 verified

`generated` 记录当前内容是如何产生的；`verified` 记录谁或什么已针对其来源或资源确认过内容。二者分开维护，因为写概念的不一定就是确认概念的。

```yaml
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
```

- `generated.by`：`generated` 内**必填**。一个参与者（§7）。
- `generated.at`：标记内容最后一次实质性变更的 ISO 8601 日期时间。消费者用它区分新近的编辑与过时的事实。

```yaml
verified:
  - { by: human:ahormati, at: 2026-06-25T09:00:00Z }
  - { by: process:finance-nightly, at: 2026-06-26T02:00:00Z }
```

- `verified`：验证事件列表，每个事件包含 `by`（一个参与者）和 `at`（一个 ISO 8601 日期时间）。多个条目表示多次独立检查，例如一次人工签核加一次夜间流程。"最近一次验证时间"即最新的 `at`。
- `verified` 与 `generated.at` 相互独立：内容可以在未重新确认的情况下变更，事实也可以在不重新生成的情况下被再次确认。
- 单一验证者**可以（MAY）**写成一个不带列表短横线的 `{ by, at }` 映射。消费者**必须（MUST）**将裸映射视为单元素列表：

```yaml
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
```

### 5.3 信任等级

消费者从 `verified` 派生信任等级，由低到高：

- 没有 `verified` 键 ⇒ `unverified`（未验证）。
- 仅由非 `human:` 参与者验证 ⇒ `machine-confirmed`（机器确认）。
- 由 `human:<id>` 参与者验证 ⇒ `human-reviewed`（人工复核）。

没有信任相关 frontmatter 的概念依然可被消费；消费者**必须不（MUST NOT）**拒绝它（§11）。信任等级是建议性信号，不是访问控制。

### 5.4 生命周期：status

```yaml
status: stable        # draft | stable | deprecated
```

- `draft`：尚未评审；可能不完整。
- `stable`：默认值；可供消费。
- `deprecated`：为链接与历史保留；不再是当前有效内容。

`status` 缺省 ⇒ `stable`。

### 5.5 生命周期：stale_after

```yaml
stale_after: 2026-09-23T00:00:00Z   # 内容在该时刻及之后即为过时
```

可选。一个绝对时刻。当 `now >= stale_after` 时概念即为过时（stale）。使用绝对时刻而非相对 TTL，使过时判断成为一次简单比较，无需参照概念被读取的时间。

## 6. 交叉链接与路径

### 6.1 概念之间的链接

概念**可以（MAY）**使用标准 Markdown 链接指向其他概念。支持两种形式：

- **绝对路径（bundle 相对）**：以 `/` 开头，相对于 bundle 根目录解释。这是推荐形式，因为文档在其子目录内移动时它保持稳定。
  `See the [customers table](/tables/customers.md) for the join key.`
- **相对路径**：标准 Markdown 相对路径。
  `See the [neighboring concept](./other.md).`

从概念 A 到概念 B 的链接断言了一种关系。具体种类（父子、引用、join 关联、依赖）由周围的文字传达，而非链接本身。构建图视图的消费者通常把所有链接视为无类型关系的有向边。

消费者**必须（MUST）**容忍断链：指向 bundle 中不存在目标的链接并非格式错误；它可能只是代表了尚未写下的知识。

### 6.2 取值为路径的字段

有若干字段以路径或 URI 为值：`resource`、`sources[].resource`、`computation`、`executor.resource` 和 `attester.resource`（§10）。`sources[].resource` 也可以是一个范围描述符（§5.1），此时它不是路径。每个取值为路径的字段接受：

- 绝对 URL（例如 `https://...`），
- 以 `/` 开头的 bundle 相对路径，或
- 相对路径（例如 `../computations/revenue.md`）。

### 6.3 references/ 约定

`references/` 子目录按约定将外部材料、运行指令或代码作为一等概念镜像进 bundle。来源、执行器和认证器通常指向其中（例如 `references/attesters/revenue.py`）。这是一种命名约定，不是强制要求。

## 7. 参与者约定

记录身份的字段（`generated.by`、`verified[].by`）使用统一的参与者约定：

- 智能体和工具使用 `<producer>/<version>`，例如 `reference_agent/gemini-2.5-pro`。
- 个人使用 `human:<id>`，例如 `human:ahormati`。
- 自动化流程使用 `process:<id>`，例如 `process:finance-nightly`。

划分信任等级的消费者（§5.3）以 `human:` 前缀为依据，因此对手写内容或人工确认的内容，生产者**必须（MUST）**使用该前缀。

## 8. 索引文件

`index.md` 文件**可以（MAY）**出现在任何目录中，包括 bundle 根目录。它列举目录内容以支持渐进式披露（progressive disclosure）：让人类或智能体在打开具体文档之前先看到有什么可用。

索引文件不含 frontmatter，唯一例外：bundle 根目录的 `index.md` **可以（MAY）**携带 `okf_version` 键（§12）。正文使用一个或多个小节，每个小节在一个标题下归组若干概念：

```markdown
# Section / Group Heading

* [Title 1](relative-url-1) - short description of item 1
* [Title 2](relative-url-2) - short description of item 2

# Another Section

* [Subdirectory](subdir/) - short description of the subdirectory
```

条目**应当（SHOULD）**包含所链接概念 frontmatter 中的 `description`。生产者**可以（MAY）**自动生成 index.md；当 index.md 不存在时，消费者**可以（MAY）**即时合成一个。

## 9. 日志文件

# Directory Update Log

## 10. 认证计算概念

认证计算（Attested Computation）概念不仅承载某个数值的含义，还承载一种被认可的数值计算方式，使消费者可以确认智能体运行的是被认可的计算，而不是自己即兴编写的。来源溯源（§5.1）回答"这条论断从哪来"；认证回答"这个数字是不是按我们规定的方式产出的"。OKF 记录计算本身和检查它的手段；它自己不执行任何东西。

### 10.1 计算是独立的概念

一个被认可的计算是 `type: Attested Computation` 的独立概念。需要该数值的概念（Metric、BigQuery Table）用普通 Markdown 链接指向它（§6）。三个特性促使计算成为独立概念：

- **运行时定义参数的含义。** 参数依据运行时的不同，可以是 SQL 绑定变量、dbt var 或 Python 实参。把 `runtime` 和 `parameters` 放在同一个 frontmatter 里，绑定语义便不言自明。
- **一份计算，多个消费者。** 同一个计算可以支撑一个指标、一个仪表盘概念和一份报表；作为概念，它被引用一次、多处复用。
- **信任状态按计算维度管理。** `verified`、`stale_after` 和单个认证器描述的是同一件事。收入、利润、毛利率各自独立验证和认证，这是三个概念，而不是一个 frontmatter 里的三个条目。

### 10.2 契约字段

契约（contract）就是该概念的顶层 frontmatter。除来源溯源、信任和生命周期字段族（§5）之外，认证计算概念还携带：

- `runtime`：该类型**必填**。唯一说明如何运行该计算的字段，由此决定执行器和认证器如何解释它、参数意味着什么。示例取值：`bigquery`、`postgres`、`dbt`、`python`、`Looker`。
- `parameters`：智能体可填入的、带类型、有名称的占位符列表。每个条目：`{ name, type, required }`。绑定语义遵循 `runtime`。
- `computation`：可选。指向存放计算的文件的路径（§6.2），用于替代正文内联围栏（见 §10.3）。缺省 ⇒ 正文的 `# Computation` 围栏即为计算本身。
- `executor`：计算如何被执行。`resource` 指明运行指令或代码；执行方（一个智能体，或确定性的消费者代码）照其执行。`receipt` 声明一次运行必须返回的字段，即认证器要检查的证据（例如 BigQuery 的 `job_id` 和该作业实际执行的 SQL）。
- `attester`：确定性检查。`resource` 指明接收回执并给出结论的代码（无 LLM）。它被设计为在消费者侧运行。

`resource` 背后是什么（一个 Skill、一个脚本、一个容器）是打包选择；OKF 固定的是接口，而非打包方式（§1）。

```yaml
---
type: Attested Computation
title: Revenue for fiscal year
description: Recognized revenue for a fiscal year, per Finance's definition.
status: stable
runtime: bigquery
parameters:
  - { name: year, type: integer, required: true }
executor:
  resource: references/skills/run-on-bq.md
  receipt: [job_id, executed_sql, result]
attester:
  resource: references/attesters/revenue.py
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
stale_after: 2026-09-23T00:00:00Z
sources:
  - id: rev-policy
    resource: https://wiki.acme/finance/revenue-recognition
    title: Revenue recognition policy
---

# Computation

SELECT SUM(amount) AS revenue
FROM finance.recognized_revenue
WHERE fiscal_year = @year

The computation binds only the declared `parameters`, per the recognition
policy.[^rev-policy]

[^rev-policy]: Revenue recognition policy
```

### 10.3 计算本体

计算以两种方式之一提供：

- **内联**：正文 `# Computation` 下的单个围栏代码块。适合与契约一起评审的短小计算。
- **文件**：把 `computation` 设为一个路径（§6.2）并省略正文围栏。适合较长或自动生成的计算，或者已经作为真实文件与非 OKF 工具链共享的计算。

```yaml
runtime: bigquery
computation: references/computations/lib/revenue.sql
parameters:
  - { name: year, type: integer, required: true }
```

智能体**可以（MAY）**只为已声明的参数提供取值；它**必须不（MUST NOT）**撰写或编辑计算本身。把计算与参数值绑定成可执行产物是消费者的工作，而认证器会独立地重新推导同样的绑定，与实际运行的内容做对比。由于比较的对象是回执所携带的、已展开编译的产物（`executed_sql`、`compiled_sql`），被改写的查询、被掉包的计算文件或被改动的依赖都会让检查失败。一个类型化、仅含参数的接口，正是使"被认可的计算是否真的被执行"成为机械比对而非主观判断的关键。

### 10.4 使用计算的概念

一份文档很少只涉及单个计算。一份同时讨论收入、利润和毛利率的损益表总览，保持为一个可读的概念，并为每个数字链接一个认证计算：

```markdown
---
type: Metric
title: Revenue
description: Recognized revenue for a fiscal year.
tags: [finance, revenue]
status: stable
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
---

# Definition

Recognized revenue sums `amount` over rows booked to the fiscal year,
computed by [the revenue computation](../computations/revenue.md).
```

由于每个计算都是自己的概念，收入可以是新鲜的，而利润已超过其 `stale_after`，且各自在每次运行时独立认证。把它们放在一起是目录层面的选择（一个带 `index.md` 的 `computations/` 文件夹），而不是 frontmatter 层面的。

### 10.5 消费者如何使用它（资料性说明）

本小节是资料性的（informative），不是规范性的（normative）。下文的运行时产物不存储在 bundle 中。

1. **发现**：通过 `type: Attested Computation` 发现，这是一个可提升到 index.md 的 frontmatter 信号；消费者可以直接到达，也可以沿使用它的概念的链接进入。
2. **加载**：从 frontmatter 加载契约，从正文（或 `computation` 指定的文件）加载计算。
3. **参数化**：智能体为已声明的参数提供取值。
4. **执行**：执行器运行绑定后的计算，并返回形状符合 `executor.receipt` 的回执。
5. **认证**：消费者对回执运行认证器。它确认来源（实际运行的计算等于被认可的计算绑定所声称的参数，而非智能体自写的 SQL）和保真度（展示值与回执的权威来源一致，通过 job id 重新读取，而不是取自智能体的文本）。
6. **拦截**：拒绝展示认证失败的结果；当 `now >= stale_after` 时警告或拒绝。成功时，呈现结论（例如指向作业日志的链接），使信任可见。

### 10.6 验证与认证的区别

`verified`（§5.2）与认证（attestation）是两回事，且两者都需要存在：

- `verified` 确认定义仍然符合策略。它是文档级的、慢的，记录在 bundle 中。
- 认证确认单次运行以被认可的方式产出了数值。它是按调用次的、运行时的，不存储在 bundle 中。

一个定义已过时的概念仍可能认证通过；一个刚被验证过的定义在每次运行时仍需认证——这正是两者都不可或缺的原因。

## 11. 合规性

一个 bundle 在满足以下条件时即合规于 OKF v0.2：

1. 树中每个非保留的 `.md` 文件都包含可解析的 YAML frontmatter 块。
2. 每个 frontmatter 块都包含非空的 `type` 字段。
3. 每个保留文件名（`index.md`、`log.md`）在存在时分别遵循 §8 与 §9 的结构。

当信任、生命周期、来源溯源或计算字段族存在时，生产者**应当（SHOULD）**遵循 §5 至 §10，而消费者：

- **必须（MUST）**将裸 `verified` 映射视为单元素列表（§5.2）。
- **必须不（MUST NOT）**因缺少任何可选字段族而拒绝概念（§5.3）。
- **应当（SHOULD）**仅根据本文规定的字段派生信任等级与过时状态，并且**应当（SHOULD）**呈现而非悄悄丢弃失败的认证（§10.5）。

消费者**应当（SHOULD）**把所有其他约束当作软性指引。特别地，消费者**必须不（MUST NOT）**因为以下原因拒绝一个 bundle：

- 缺少可选的 frontmatter 字段。
- 未知的 `type` 取值。
- 未知的附加 frontmatter 键。
- 断链的交叉链接。
- 缺失的 index.md 文件。

## 12. 版本管理

本文档规定 OKF 0.2 版本。修订按 `<major>.<minor>` 版本化：

- 次版本（minor）升级引入向后兼容的增量（新的可选字段、新的约定小节标题）。
- 主版本（major）升级可能做出破坏性变更（重命名必填字段、变更保留文件名）。

bundle **可以（MAY）**在 bundle 根目录 `index.md` 的 frontmatter 块中用 `okf_version: "0.2"` 声明其目标版本（这是 index.md 中唯一允许出现 frontmatter 的地方）。不理解所声明版本的消费者**应当（SHOULD）**尽力消费（best-effort），而不是拒绝该 bundle。

### 已考虑但推迟的事项

以下事项刻意留给未来的修订版本：

- 完整的运行时协议：回执与结论的线上格式（wire format），以及围绕一次运行的认证生命周期。
- 认证器的 ABI、可移植性与沙箱化，可能与未来关于 serving 和 Skills 的工作一起打包。
- 认证缓存。
- 语义层模板（Looker、dbt），届时认证器的比较从 SQL 相等性转变为模型与绑定的相等性。

## 13. 相对于 v0.1 的变更

v0.2 取代 OKF v0.1，按 §12 属于次版本升级，除了下面特意标注的两处破坏性变更——因为它们重命名或退役了 v0.1 的字段。一个 v0.1 bundle 在本文注明的回退机制下，可被 v0.2 消费者消费。

### 13.1 破坏性变更

- `timestamp` 被 `generated.at` 取代。概念的最后一次内容变更现在记录为 `generated: { by, at }`（§5.2）。当 `generated` 缺省时，消费者**可以（MAY）**回退到旧版 `timestamp`。
- 正文中的 `# Citations` 列表被 `sources` 取代。来源溯源移入 frontmatter（§5.1）。消费者**应当（SHOULD）**读取 `sources`，并且**可以（MAY）**继续为 v0.1 文档解析旧版正文中的 `# Citations` 列表。

### 13.2 增量变更

以下全部是增量变更：新的可选键、一种新概念类型和一个新的约定标题。它们的缺省产生的就是一个普通的 v0.1 概念。

- 新的 frontmatter 字段族：`sources` 及其按来源的可信度信号（`author`、`usage_count`、`last_modified`）与同级字段 `usage_window`；`generated`、`verified`；`status`、`stale_after`（§5）。
- 新概念类型 `Attested Computation` 及其计算键 `runtime`、`parameters`、`computation`、`executor`、`attester`（§10）。
- 新的约定正文标题 `# Computation`（§4.2）。
- `generated.by` 与 `verified[].by` 的参与者约定（§7）。

其余一切（bundle 结构、保留文件名、必填的 `type`、推荐的 `title`/`description`/`resource`/`tags`、交叉链接、索引文件、日志文件、宽容的合规性）原样沿用。

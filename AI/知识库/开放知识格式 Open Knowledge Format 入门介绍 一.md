> 基于 v0.1 版本

随着基础模型不断进步，缺少相关上下文往往会限制它们的能力，尤其是在使用这些模型构建智能体系统时。模型可以帮助你编写代码、总结文档或分析数据集，但它们仍然需要正确的信息，才能产出准确且可付诸行动的结果。

因此，我们今天正式推出开放知识格式（Open Knowledge Format，OKF）。这是一项开放规范，将 LLM Wiki 模式正式定义为一种可移植、可互操作的格式。它不依赖任何厂商，对智能体和人类都很友好，可用于表示现代 AI 系统所需的元数据、上下文和经过整理的知识。

当前发布的 OKF v0.1 将知识表示为一个由 Markdown 文件组成的目录，每个文件都带有 YAML 前置元数据。规范只约定了少量规则，使不同生产者编写的 Wiki 无需转换，就能被不同智能体直接使用。

就这么简单。没有复杂的压缩方案，没有新的运行时，也不要求使用 SDK。一组 OKF 文档就是：
- **纯 Markdown**：可在任何编辑器中阅读，可在 GitHub 上渲染，也能被任意搜索工具建立索引。
- **就是文件**：可打包为 tar 文件传输，可托管在任意 Git 仓库中，也可挂载到任何文件系统。
- **标准 YAML 前置元数据**：只为少量需要查询的结构化字段服务，包括 `type`、`title`、`description`、`resource`、`tags` 和 `timestamp`。

如果你使用过 Obsidian、Notion、Hugo，或者过去一年中出现的任何 LLM Wiki 模式，那么这种结构会让你感到熟悉。OKF 所做的，就是正式定义一组最小规则，让这些模式能够相互兼容。

下面我们来看看：OKF 能为你的组织解决什么问题、它如何运作、怎样开始使用，以及未来将走向何方。

## 1. 碎片化的上下文生态

在大多数公司中，基础模型使用的信息绝大部分来自内部知识，例如：数据表 Schema、某个指标的业务含义、事故处理手册、两个系统之间的关联路径，以及旧 API 的弃用通知等。

如今，这些知识单元分散在各种彼此割裂的系统中：
- 各自拥有独立 API 的元数据目录；
- Wiki、第三方系统或共享云盘；
- 代码注释、文档字符串或 Notebook 单元格；
- 少数资深工程师的头脑中。

当 AI 智能体需要回答“如何根据事件流计算周活跃用户数？”时，它必须从这些分散且互不兼容的载体中拼装答案。每家厂商都有自己的数据目录、SDK 和知识图谱 Schema，但这些知识很难在不同产品或组织之间移植。

结果就是：每个智能体开发团队都要从零开始解决同一个上下文组装问题；每个数据目录厂商都在重复设计相同的数据模型；而知识本身则被锁定在创建它的系统中。

## 2. 将知识构建成持续演进的 Wiki

开发团队正在改变构建 AI 智能体的方式。与其让模型反复搜索相同文档、寻找相同事实，不如为智能体提供一个共享的 Markdown 知识库，并让知识库持续积累价值。这样，智能体可以承担读取和更新自身文件的繁琐工作，而团队则负责整理内容，并像管理代码一样管理知识。

知名 AI 研究者和教育者 Andrej Karpathy 在他的 [LLM Wiki Gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 中对这一理念做了非常精辟的概括。他写道：“LLM 不会感到厌烦，不会忘记更新交叉引用，而且一次就能修改 15 个文件。”那些让人们最终放弃个人 Wiki 的繁琐维护工作，恰恰是 LLM 所擅长的。

类似的“知识即 Wiki”模式正以不同名称反复出现：与编程智能体相连接的 Obsidian 知识库；`AGENTS.md`、`CLAUDE.md` 这一类约定文件；包含大量 `index.md` 和 `log.md`、供智能体在开展实际工作前查阅的代码仓库；以及数据团队内部的“元数据即代码”仓库。

这种模式既有吸引力，也十分强大，但每种实现都各自为政。Karpathy 的 Wiki、你的团队 Wiki，以及厂商导出的数据目录，看起来可能都很相似——都使用 Markdown、前置元数据和交叉链接——但它们在设计时并未考虑彼此协作。业界尚未就每份文档必须包含哪些字段、不同文件名分别代表什么达成共识。因此，Wiki 中编码的知识仍然被困在原始团队内部，每当构建新的智能体时，相关工作都要重复一遍。

## 3. 缺少的是一种格式，而不是另一项服务

解决这个问题不需要再造一个知识服务。我们真正需要的是一种知识表示格式，并且它应满足以下要求：
- 任何人都能生产，无需 SDK；
- 任何人都能消费，无需系统集成；
- 在不同系统、公司和工具之间迁移后仍然有效；
- 与其所描述的代码一起存放在版本控制系统中；
- 人类可以阅读，智能体也可以解析——使用同一份文件，无需转换层。

OKF 从设计之初就是为了成为这样的格式。

## 4. OKF 如何运作：一屏看懂设计

一个 OKF 知识包就是一个 Markdown 文件目录，其中的文件用于表示各种概念，包括数据表、数据集、指标和 API 等任何你想记录的内容。每个概念对应一个文件，文件路径就是该概念的身份标识：
```text
sales/
├── index.md
├── datasets/
│   ├── index.md
│   └── orders_db.md
├── tables/
│   ├── index.md
│   ├── orders.md
│   └── customers.md
└── metrics/
    ├── index.md
    └── weekly_active_users.md
```

每份概念文档都包含一小段 YAML 前置元数据，用于存放结构化字段；其余内容则写在 Markdown 正文中：
```markdown
---
type: BigQuery Table
title: 订单
description: 每行代表一笔已完成的客户订单。
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, revenue]
timestamp: 2026-05-28T14:30:00Z
---

# Schema

| 列 | 类型 | 说明 |
|---|---|---|
| `order_id` | STRING | 全局唯一的订单标识符。 |
| `customer_id` | STRING | 指向 [customers](/tables/customers.md) 的外键。 |

# 关联

通过 `customer_id` 与 [customers](/tables/customers.md) 关联。
```

各个概念通过普通 Markdown 链接彼此连接，把目录转变成一张关系图。这张图表达的关系比文件系统隐含的父子关系更加丰富。知识包还可以选择包含 `index.md` 文件，以便智能体在逐层浏览目录时进行渐进式披露；也可以包含 `log.md` 文件，按时间顺序记录变更历史。

完整的 [规范](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) 只有一页，其中包括一致性标准、交叉链接规则和少量保留文件名。

## 5. 设计背后的三项原则

- **最小约束。** OKF 对每个概念只强制要求一项内容：`type` 字段。其余部分——例如存在哪些类型、还要包含哪些字段、正文由哪些章节组成——都由生产者自行决定。规范定义的是互操作边界，而不是内容模型。
- **生产者与消费者相互独立。** OKF 清晰地分离了知识的编写者和使用者。人类手工编写的知识包可以被 AI 智能体使用；元数据导出流水线生成的知识包可以在可视化工具中浏览；一个 LLM 合成的知识包可以由另一个 LLM 查询。格式就是双方之间的契约，任意一端的工具都可以独立替换。
- **它是格式，而不是平台。** OKF 不绑定任何特定云平台、数据库、模型提供商或智能体框架。读取、编写或提供 OKF 内容，永远不需要专有账号或 SDK。我们将它发布为开放标准，是因为知识格式的价值取决于有多少参与者采用它，而不是谁拥有它。

## 6. 与规范一同发布的内容

为了让这种格式真正落地，我们同时发布了生产端和消费端的参考实现：
- **知识增强智能体**：遍历 BigQuery 数据集，为每个数据表和视图起草一份 OKF 概念文档；随后进行第二轮 LLM 处理，抓取权威文档，并用引用、Schema 和关联路径丰富每个概念。
- **静态 HTML 可视化工具**：将任意 OKF 知识包转换成一个交互式关系图，并封装在单个自包含文件中；使用者一侧不需要后端、不需要安装任何软件，也不会有数据离开当前页面。
- **三个可直接浏览的示例知识包**：分别基于 [GA4 电商](https://developers.google.com/analytics/bigquery/web-ecommerce-demo-dataset)、[Stack Overflow](https://console.cloud.google.com/bigquery?ws=!1m4!1m3!3m2!1sbigquery-public-data!2sstackoverflow) 和 [Bitcoin 公共数据集](https://cloud.google.com/blog/topics/public-datasets/bitcoin-in-bigquery-blockchain-analytics-on-public-data?e=48754805)。它们由参考智能体生成并提交到代码仓库，作为持续更新且符合 OKF 规范的示例。

这些实现有意被定位为概念验证。知识增强智能体只展示了生产 OKF 的一种方式；OKF 格式本身并不要求使用特定的智能体框架或 LLM。可视化工具也只展示了一种消费方式；OKF 格式本身并不要求使用 HTML 或关系图。我们期待——也非常希望——生产者和消费者生态远远超越目前发布的这些工具。

## 7. 下一步

OKF v0.1 是一个起点，而不是一项已经完成的标准。随着更多生产者和消费者出现，以及我们共同了解智能体在实践中真正需要怎样的知识表示方式，这一格式还会继续演进。

我们从第一天起就以开放方式发布 OKF，因为知识格式只有开放才能名副其实。无论你是在构建知识目录、知识增强流水线、面向 AI 智能体的 Wiki，还是 AI 知识领域中的任何其他系统，都是如此。

接下来，我们鼓励你：
- 阅读[规范](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)；
- 为你的源系统、数据库或文档站点编写一个生产者；
- 编写一个消费者，例如查看器、搜索索引，或能够基于知识包进行推理的智能体；
- 使用你自己的数据试用参考实现；
- 提交 Issue、发起 PR 或提出扩展建议：该规范采用版本化管理，并明确支持向后兼容的持续演进。

代码仓库、规范和示例知识包均已发布在 [GitHub](https://github.com/GoogleCloudPlatform/knowledge-catalog)。我们还更新了 Google Cloud 的 Knowledge Catalog，使其能够摄取开放知识格式，并将其提供给我们的智能体。相关代码和示例都可以在该代码仓库中找到。

这种格式本身就是贡献。我们发布的工具旨在让它真正可用，并降低尝试使用它的成本。无论你的知识今天以何种形式存在，OKF 都致力于成为未来交换知识时使用的通用语言。
